==========================================================
Oracle Gap 诊断方案（回工位照着跑）
创建：2026-09-02
针对症状：进化"搜得动，搜不出更好的"——曲线在动，PRD 卡在 4.59%
==========================================================

【为什么要先做这个，而不是继续改进化】
已经在"怎么搜"这条轴上试了两次：
  第一次：ID 菜单选组件      → 停滞
  第二次：改成 LLM 生成/变异 → 还是停滞（本次反馈）
同一条轴上连续两次失败，通常说明瓶颈不在搜索方式，而在天花板本身。
本诊断用你硬盘上已有的评估结果，零 LLM 调用、零训练，一个下午出结论。
结论直接决定下一步该做什么——数字出来之前，任何进一步改动都是在猜。

==========================================================
一、核心思路：把三个可能的死因一次排查完
==========================================================

死因 1：找错了目标
  你一直在找"一个在所有实例上最好的算法"（single best solver, SBS）。
  但如果不同算法各擅长不同实例，那么"每实例挑最好的"（oracle / VBS）
  会显著优于 SBS。这个差距叫 oracle gap。
  → 如果 gap 大：改成"实例→算法 的映射"就能拿到增益，且这个增益是
    结构性保证的，不依赖 LLM 灵光一闪。算法选择领域几十年的定论。

死因 2：算法池同质
  生成的算子换了名字、换了代码，但在实例上的实际行为几乎一样
  （都退化成同一类局部搜索）。这种情况下池子里根本没有更好的东西可挑，
  换搜索算子、上 DPO/GRPO 全都不会有用。
  → 瓶颈在组件表示层，不在搜索层。

死因 3：改进被噪声淹了
  单 seed 评估的噪声可能比真实代际改进还大。看起来"搜不出更好的"，
  实际是"改进量小于噪声，看不见"。

三个死因的处方完全不同，所以必须先分清是哪个。

==========================================================
二、关键方法：怎么避免得出假结论
==========================================================

★ 陷阱一：胜者诅咒（winner's curse）
  如果用同一批 seed 既挑算法又报成绩，oracle 会虚高——每个实例都在挑
  "这次运气最好的那个"，把噪声当成了本领。
  做法：seed 分两组。A 组结果用来挑算法，B 组结果用来报成绩。
        脚本已内置（默认对半分），单 seed 会警告。

★ 陷阱二：把"实例难度"误当成"算法互补"
  大实例对所有算法都难，PRD 都高。直接算相关性会被这个共同成分主导，
  看上去算法都差不多（或都很像），得不出结论。
  做法：二维方差分解。把 PRD 矩阵拆成
        实例效应（这实例本来就难）
      + 算法效应（这算法整体就弱）
      + 交互残差（这算法在这实例上特别行 ← 只有这部分是真互补）
  然后拿交互残差的强度和 seed 噪声比：
        交互/噪声 > 2    → 有真实特化
        交互/噪声 < 1.3  → 各有所长基本是随机波动，池子同质
  这是本诊断的核心判据，比单看 oracle gap 可靠得多。

==========================================================
三、准备数据（唯一需要你动手的地方）
==========================================================

把历史上生成过的所有算法（各代、各种群成员，全捞出来，不要只留精英）
在测试集上的评估结果整理成一个 csv：

results.csv
  algo_id, instance_id, seed, makespan [, generation]
  A00, j30c5e1, 0, 1523
  A00, j30c5e1, 1, 1531
  A01, j30c5e1, 0, 1498
  ...
  generation 列可选，有的话会顺便画进化曲线。

bks.csv
  instance_id, bks
  j30c5e1, 1476
  ...

seed 数：至少 3 个，5~10 最好。这是整个诊断的前提——
  只有 1 个 seed 结论不可信，脚本会警告但仍会跑。
  如果历史数据是单 seed 跑的，先补跑 seed（这是改动清单阶段一"多 seed"，
  本来就要做，不算额外工作）。

==========================================================
四、运行
==========================================================

  cd 论文_LLM自进化启发式算法
  python3 oracle_gap.py --results results.csv --bks bks.csv --out report

  依赖只有 numpy + pandas（你工位机器上 2.0.2 / 2.3.3 已装）。

输出：
  report.txt                — 完整诊断报告 + 自动结论
  report_per_instance.csv   — 逐实例明细，按"每实例选对算法能省多少"降序
                              （挑前几行当论文案例分析用）

==========================================================
五、看结果：三种结局和各自的处方
==========================================================

■ 结局一：交互/噪声比 > 2 且相对 gap ≥ 15%
  含义：算法池是健康的，算法确实各有所长。
  诊断：你的方法没问题，是目标设错了——一直在找单个最优解。
  处方：转向"每实例自适应选择/条件生成"。
        这正是原计划第二篇的核心。如果第一篇卡住，考虑把它提前——
        因为它的增益有结构性保证，而"生成更强的单一算法"没有。
  论文写法：报 SBS vs Oracle vs 你的选择器三条线，
            oracle 是天花板，选择器越接近它越好。这是算法选择领域
            的标准叙事，审稿人熟悉且认可。

■ 结局二：交互/噪声比 < 1.3
  含义：算法池同质。生成的东西行为上是一回事。
  诊断：瓶颈在组件表示层，不在搜索层。可能是组件粒度切太粗，
        或所有组合最终都退化成同一类局部搜索行为。
  处方（二选一，建议同时准备）：
    (a) 重做组件空间——细化粒度、加入行为差异大的算子族
        （不同邻域结构、不同解表示、不同重启策略）。
        重做后再跑一次本诊断，看交互/噪声比有没有起来。
    (b) 换论文主张——这是更稳的路。见第六节。
  ⚠ 关键：这个结局下，绝对不要上 DPO/GRPO 微调。
    池子里没有更好的东西，微调只会把当前的塌缩固化进模型权重。

■ 结局三：灰区（1.3 ~ 2）
  先加 seed 到 8~10 把噪声压下去重测。噪声降低后交互/噪声比会上升，
  灰区常常是 seed 不够导致的假象。

■ 附加信号（不管哪个结局都要看）
  · 赢家集中度 > 50%：单个算法霸占多数实例的最优
    → 这是"策略塌缩"的直接量化证据，可以直接做成论文里的图。
      这个数字本身就是创新点②的实验材料。
  · oracle PRD 为负：你的算法打破了 BKS
    → 要么 BKS 表过旧（已在待办里），要么评估器有 bug。先查这个，
      因为它会让所有 PRD 数字失去意义。
  · 进化曲线不单调下降 → 精英保留或选择压力有 bug，先修这个。

==========================================================
六、如果落在结局二：论文主张要换（重要）
==========================================================

双创新点里，②"刻画并解决塌缩现象"本来就是定的主攻保底项。
这条路的关键好处：塌缩本身就是结果，不需要赢过 PRTS/CSA。

可以诚实且有价值地写成：
  LLM 进化在组合优化上为什么会塌缩
  → 塌缩的机制是什么（用交互/噪声比、赢家集中度量化）
  → 什么机制能缓解（多样性控制、insight archive 的消融）
  → 缓解到什么程度仍有上限（这是诚实的负面结论，有价值）

这和 LLaMEA 那批文献的观察互相印证——它们的结论就是"LLM 进化常常
只是把少数已知策略重新发现一遍，难赢强 baseline"。你的数据正好为
这个现象提供了机制层面的量化解释。

反过来，如果一直试图证明"我的方法能生成更强算法"而事实上不能，
这篇会越写越难，审稿人一眼看出来。

⚠ 但不要现在就换定位。先跑诊断，让数字决定。

==========================================================
七、执行顺序
==========================================================
[ ] 1. 整理 results.csv / bks.csv（历史算法全捞，别只留精英）
[ ] 2. 确认 seed ≥ 3；不够就先补跑
[ ] 3. 跑 oracle_gap.py，读 report.txt 的"结论"段
[ ] 4. 先处理附加信号里的 bug 类问题（oracle 为负 / 曲线不单调）
[ ] 5. 按结局一/二/三选处方
[ ] 6. 结局落定后再回来决定：BKS 重算的优先级、DPO 上不上

注：BKS 表过旧这件事会影响 PRD 绝对值，但不影响本诊断的结论——
    因为 oracle gap 是同一张 BKS 表下的相对比较，表偏了两边一起偏。
    所以不必等 BKS 重算完再做诊断，可以并行。
